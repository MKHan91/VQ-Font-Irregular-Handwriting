# 심사 대응 추가 실험 키트 (electronics-4654524)

이 키트는 심사위원 1·2가 요구한 실험 중 GPU가 필요한 것만 모아 둔 것입니다. 나머지 분석(H4 재분석, 구조 통제, 콘텐츠 폰트 비교, 참고문헌 검증 등)은 이미 CPU에서 끝냈습니다.
아래 순서대로 실행한 뒤 결과 묶음(`revision_results.tar.gz`)을 보내 주시면, 수치는 받은 결과로만 원고에 넣습니다. 실행하지 못한 블록은 원고와 답변서에 "수행하지 못함"으로 정직하게 적습니다.

## 1. 준비 (10분)

1. 키트 폴더를 VQ-Font 프로젝트 루트(`train.py`, `inference.py`가 있는 폴더)에 `revision_kit/` 이름으로 복사합니다.
2. `revision_kit/run_revision.sh` 맨 위 경로 블록을 실제 경로로 고칩니다.
   - `STAGE0_CKPT` : Stage 0 VQGAN 체크포인트 (`epoch=000781.ckpt`)
   - `STAGE1_CKPT` : Stage 1 체크포인트 (`vq_font_v4.0/last.ckpt`)
   - `STAGE2_CKPT` : Stage 2 체크포인트 (`brush_finetune_v2/last.ckpt`)
   - `REFS` : 손글씨 78자 폴더 (`reference_images_v2`)
   - `CONTENT` : 콘텐츠 폰트 이미지 폴더 (NanumBarunpenR)
   - `CR_MAP` : 원 논문에 쓴 `cr_mapping_v2.json`
   - `META1` / `META2` : Stage 1, Stage 2 학습에 실제로 쓴 meta json (같은 파일이면 둘 다 같은 경로)
   - `FT_CFG` : Stage 2 설정 파일 (`cfgs/custom_finetune.yaml`)
   - `ORIG_GEN` : 원 논문의 생성 결과 11,172장 폴더 (PROBE 블록이 채점)
4. `probe.pt`(자모 인식 프로브 가중치)는 키트에 들어 있습니다. 프로브는 Stage 1 폰트 폴더로만 학습했고, 손글씨 78자와 생성 이미지는 학습에 쓰지 않았습니다.
3. `rk_patch.py`는 원본 코드를 고치기 전에 `*.rk_orig` 백업을 만듭니다. 환경변수를 주지 않으면 원래 동작과 똑같습니다.

## 2. 실행 순서와 예상 시간 (RTX 3090 기준 추정)

| 순서 | 명령 | 하는 일 | 답하는 심사 의견 | 예상 시간 |
|---|---|---|---|---|
| 1 | `bash revision_kit/run_revision.sh E0` | 체크포인트 간 파라미터 비교(어떤 층이 실제로 학습되었는지), meta 내용 확인, 자기 제외 매핑·5-fold 분할 생성 | 원고-코드 불일치 확인 (필수) | 5–10분 |
| 2 | `... E1` | 대상 글자를 참조에서 뺀 상태로 78자 재생성: Stage 2와 Stage-1-only 각각 | R1-2, R2-4 (자기 포함 편향) | 10분 |
| 3 | `... E2` | Stage-1-only로 11,172자 전체 생성 | R1-1, R2-3 (Stage-1-only 정량 비교) | 약 3시간 |
| 4 | `... E3` | 5-fold 보류 검증: 각 fold에서 62–63자로 Stage 2를 다시 학습하고 남은 15–16자로 PSNR/SSIM/LPIPS 측정, Stage-1-only와 비교 | R1-3, R2-4 (일반화 검증) | 5–10시간 |
| 5 | `... E5` | from-scratch 대조군(H2): 생성기를 무작위 초기화해 78자만으로 학습 후 전체 생성, 그리고 fold별 보류 검증 | R1-1, R2-5 | 8–15시간 |
| 6 | `... E4` | 절제 실험: 동결 해제(B), 잠재 증강 제거(C) | R1-3 | 10–20시간 (시간이 부족하면 생략 가능) |
| 7 | `... PROBE` | 자모 인식 프로브로 원 논문 생성본 11,172자, Stage-1-only 생성본(E2), from-scratch 생성본(E5)을 채점하고 H2의 McNemar 검정 실행 | R2-5(b), H2 | 수 분 (GPU 불필요) |
| 8 | `... PACK` | 결과 묶음 만들기 (체크포인트 제외) | – | 수 분 |

- 한 번에 모두 돌리려면 `bash revision_kit/run_revision.sh ALL` (순서: E0, E1, E2, E3, E5, PROBE, E4, PACK).
- 터미널이 끊겨도 계속 돌도록 `nohup bash revision_kit/run_revision.sh ALL > rk_all.log 2>&1 &` 를 권합니다.
- 각 블록의 소요 시간은 `revision_runs/run_log.txt`에 자동 기록됩니다. 원고 Table 1의 "대략적 기억" 대신 실측 시간을 쓰는 근거가 됩니다.
- 학습 반복 수는 모든 학습 조건에서 41,500으로 같고, 시드는 2입니다. 시간이 남으면 `SEEDS="2 3 4"`로 늘리면 됩니다.

## 3. 시간이 부족할 때의 우선순위

1. E0, E1, E2 (반드시, 합계 약 3–4시간)
2. E3 (H3의 독립 검증. 심사위원 둘 다 요구)
3. E5 (H2. 심사위원 둘 다 요구. 최소한 전체 78자 학습 1회 + 전체 생성)
4. E4 (심사위원 1만 요구)

E4까지 못 하면 답변서에 이유(연산 시간)와 대신 제공한 증거를 적습니다. 결과를 지어내지 않습니다.

## 4. 보내 주실 것

1. `revision_results.tar.gz` (PACK 결과). 생성 이미지, 측정 CSV, 학습 로그, 파라미터 감사 결과가 들어 있습니다.
2. 원 논문의 전체 생성 결과 폴더: `inference_results/target_style_images/reference_images_v2/images` (11,172장, zip으로). 원고 분석에 쓴 것과 같은 파일인지 확인하고, LPIPS와 프로브 점수를 계산하는 데 씁니다.
3. 기존 학습 로그 폴더 `vq_font_results/logs/` (Stage 1·2 로그의 설정 덤프로 batch size, d_lr을 확인합니다. GitHub의 `custom_finetune.yaml`은 batch 16, d_lr 8e-5인데 원고 Table 1은 32, 8e-4로 되어 있습니다).

## 5. 실행 전에 확인해 주실 질문

원고와 답변서에서 노란색 `[[...]]`로 표시한 부분은 아래 답과 실험 결과로만 채웁니다.

1. meta 파일 내용: Stage 1과 Stage 2에 실제로 쓴 meta json에 어떤 폰트가 들어 있었습니까? 코드상으로는 Stage 2 meta에 손글씨 외 폰트가 있으면 25% 확률로 그 폰트에서 학습 샘플을 뽑습니다. 특히 Stage 1 meta에 `reference_images_v2`(손글씨 78자)가 들어 있었는지 확인이 필요합니다. 들어 있었다면 Stage-1-only 결과도 78자를 이미 본 모델이 됩니다. (E0가 자동으로 목록을 만듭니다.)
2. 폰트 수: 공개 데이터의 Stage 1 폴더는 77개(UhBee 68 + 기타 9), 글자 수 267,185입니다. 원 원고의 76개(UhBee 67)와 다릅니다. 원고에는 `[[77]]`, `[[68]]`로 표시해 두었습니다.
3. BMKIRANGHAERANG 폴더의 빈 이미지 8,693장이 Stage 1 학습에 그대로 들어갔습니까?
4. `inference.py`가 `generator_ema` 가중치를 쓰는 것이 맞습니까?
5. 앞 논문[3]과의 관계: (a) [3]의 실험 2(비정형 현대 서체)에 쓴 글자가 이번 78자와 같은 작가의 손글씨입니까? (b) [3]의 체크포인트, 학습 결과, 수치 중 이번 논문에 다시 쓴 것이 있습니까? 원고 1장과 답변서에 "재사용 없음"으로 적어 두었고 노란색으로 표시했습니다. 사실과 다르면 알려 주세요.
6. Stage 1 학습 때 인코더 동결이 켜져 있었습니까? 공개된 `train.py`는 매 실행마다 성분·콘텐츠 인코더를 동결합니다. Stage 1도 같은 코드로 돌렸다면 Stage 1의 인코더는 사전학습 가중치에서 바뀌지 않았다는 뜻이 됩니다. E0의 체크포인트 비교로 확인합니다.
7. 잠재 증강(노이즈)이 Stage 1에도 켜져 있었습니까?
8. Hugging Face 저장소의 `ttf.zip`(폰트 파일 묶음)을 삭제할지, 폰트별 라이선스를 적어 남겨 둘지 정해 주세요. 원고 데이터 가용성 문장에 표시해 두었습니다.
9. 추가 실험(GPU)은 누가 돌렸습니까? 감사의 글에 "the authors ran"이라고 적었습니다.
10. 블라인드 평가(심사위원 2 의견 5(d)): 이번 수정에서는 하지 않은 것으로 답변서에 이유를 적었습니다. 학위논문의 전문가 평가 패널 등으로 작은 규모라도 가능하면 알려 주세요. 사람 평가자를 쓰면 원고의 IRB·동의 문구도 바뀌어야 합니다.
11. 앞 논문[3]의 기준 모델(DM-Font, Diff-Font)을 같은 5-fold로 미세조정하는 E6를 할 수 있습니까? 못 하면 원고와 답변서의 E6 문장을 "수행하지 못함"과 이유로 바꿉니다.

실험이 끝나면 원고 쪽수·줄 번호가 바뀌므로, 답변서의 위치 표시는 최종 수치를 넣은 뒤 다시 계산합니다.

## 6. 문제가 생기면

- 오류 메시지 마지막 30줄과 `revision_runs/run_log.txt`를 보내 주세요.
- `rk_patch.py`를 되돌리려면 `*.rk_orig` 파일을 원래 이름으로 복사하면 됩니다.
